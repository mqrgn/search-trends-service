# Search Trends Service

Highload сервис для отображения топа самых популярных поисковых запросов в реальном времени.

## Описание

Сервис читает поток поисковых событий из NATS и предоставляет API для получения топ-N запросов за последние 5 минут. Реализован с учетом highload требований: запросов на чтение в 10-50 раз больше, чем входящих событий.

## Архитектура

### Контракт данных

Формат payload в NATS:

```json
{
  "query": "iphone 15",
  "timestamp": 1716465559,
  "user_id": "uuid-user-123",
  "session_id": "uuid-session-456"
}
```

**Обоснование полей:**

- `query` (string) — поисковый запрос пользователя. Основное поле для агрегации.
- `timestamp` (int64) — Unix timestamp события. Необходим для реализации sliding window на 5 минут.
- `user_id` (string) — идентификатор пользователя. Используется для детекции аномальных всплесков (один пользователь спамит одинаковые запросы).
- `session_id` (string) — идентификатор сессии. Дополнительная метрика для анализа поведения и детекции ботов.

### Структуры данных

**Sliding Window с бакетами:**

Для хранения данных за 5 минут используется массив из 5 бакетов по 1 минуте каждый:

```
[Bucket 0] [Bucket 1] [Bucket 2] [Bucket 3] [Bucket 4]
   1 min      1 min      1 min      1 min      1 min
```

Каждый бакет содержит `map[string]*QueryStats`, где:
- Ключ — поисковый запрос
- Значение — статистика (счетчик, уникальные юзеры, уникальные сессии)

**Почему именно эта структура:**

1. **O(1) запись** — добавление события в текущий бакет
2. **O(N) чтение** — агрегация по 5 бакетам, где N — количество уникальных запросов
3. **Автоматическая очистка** — старые бакеты перезаписываются при ротации
4. **Память** — фиксированный размер окна, нет утечек памяти

**RWMutex для конкурентности:**

- Много читателей (API запросы) могут работать параллельно
- Писатели (консьюмер) блокируют только на время записи
- Идеально для соотношения read/write 10-50:1

### Защита от накруток

Реализован механизм детекции аномальных всплесков:

```go
ratio = total_count / unique_users

if ratio > 10 {
    score = total_count / (ratio / 10)
}
```

Если один пользователь делает слишком много одинаковых запросов, его вес снижается. Например:
- 100 запросов от 1 пользователя → score = 10 (вместо 100)
- 100 запросов от 100 пользователей → score = 100

### Стоп-лист

Динамический стоп-лист реализован через `map[string]struct{}`:
- O(1) проверка при добавлении события
- O(1) добавление/удаление через API
- Изменения применяются мгновенно без перезапуска

## API

### Получить топ запросов

```bash

```

**Response:**
```json

  "queries": [
```

## Быстрый старт

### Через Docker Compose (рекомендуется)

```bash
docker-compose up --build
```

Сервис будет доступен на `http://localhost:8080`

### Локальный запуск

**1. Запустить NATS:**
```bash
docker run -p 4222:4222 -p 8222:8222 nats:latest -js -m 8222
```

**2. Собрать и запустить сервис:**
```bash
go build -o server ./cmd/server
./server
```

**3. (Опционально) Запустить producer для тестирования:**
```bash
go build -o producer ./cmd/producer
./producer
```

### Переменные окружения

```bash
NATS_URL=nats://localhost:4222
NATS_SUBJECT=search.events
HTTP_PORT=8080
```

## Trade-offs и решения

### 1. In-memory хранилище vs БД

**Решение:** In-memory

**Почему:**
- Окно всего 5 минут — данные помещаются в память
- Латентность < 1ms для чтения топа
- Нет overhead на сериализацию/десериализацию
- Простота архитектуры

**Trade-off:** При рестарте данные теряются, но это приемлемо для окна в 5 минут.

### 2. Кеширование топа vs вычисление на лету

**Решение:** Вычисление на лету с throttling (раз в секунду)

**Почему:**
- Данные меняются постоянно
- Кеш устаревает слишком быстро
- Вычисление топа быстрое (O(N log N), где N — уникальные запросы)

**Trade-off:** Небольшая задержка при первом запросе после секунды, но это незаметно.

### 3. Точность vs производительность в детекции накруток

**Решение:** Простой ratio-based алгоритм

**Почему:**
- O(1) вычисление при агрегации
- Не требует дополнительных структур данных
- Эффективно ловит очевидные накрутки

**Trade-off:** Может пропустить сложные паттерны накруток (распределенные боты), но для MVP достаточно.

### 4. NATS vs Kafka

**Решение:** NATS

**Почему:**
- Легковесный и быстрый
- Простая настройка для локального запуска
- Достаточная производительность для задачи
- Меньше overhead

**Trade-off:** Kafka более надежен для production (репликация, персистентность), но для этой задачи избыточен.

### 5. Размер бакета (1 минута)

**Решение:** 5 бакетов по 1 минуте

**Почему:**
- Баланс между точностью и производительностью
- Меньше бакетов → меньше итераций при агрегации
- 1 минута — достаточная гранулярность для трендов

**Trade-off:** Можно было сделать 300 бакетов по 1 секунде для большей точности, но это увеличило бы overhead.

## Проблемы в постановке задачи и решения

### 1. Не указан формат payload

**Проблема:** Смежная команда не знает, что отправлять.

**Решение:** Спроектирован контракт с минимально необходимыми полями для выполнения всех требований.

### 2. "Аномальные всплески" — нет критериев

**Проблема:** Что считать аномалией?

**Решение:** Реализован ratio-based подход: если один пользователь делает слишком много одинаковых запросов, снижаем вес. Порог можно настроить.

### 3. Нет требований к персистентности

**Проблема:** Что делать при рестарте?

**Решение:** Для окна в 5 минут персистентность не критична. Сервис стартует с пустым состоянием и быстро наполняется.

### 4. "Максимально быстро" — нет SLA

**Проблема:** Какая латентность приемлема?

**Решение:** Оптимизировано под < 1ms для чтения топа при нормальной нагрузке. Можно измерить бенчмарками.


```
BenchmarkTrendStorage_AddEvent-12         26011015    45.35 ns/op       0 B/op    0 allocs/op
BenchmarkTrendStorage_GetTopQueries-12        7570   156307 ns/op  154187 B/op 1110 allocs/op
```

**Анализ производительности:**

- **AddEvent:** ~45 ns/op, 0 аллокаций — запись событий экстремально быстрая
- **GetTopQueries:** ~156 μs/op — чтение топа занимает микросекунды
- При нагрузке 10000 RPS на запись, сервис может обрабатывать **~6400 RPS на чтение** 
- Это **значительно превышает** требование 10-50x больше чтений

### Нагрузочное тестирование

Используем `hey` для нагрузочного тестирования:

```bash
# Запустить готовый скрипт
bash load_test.sh

# Или вручную
go install github.com/rakyll/hey@latest
hey -n 100000 -c 100 http://localhost:8080/api/v1/top?limit=10
```

**Ожидаемые результаты:**

При 100 одновременных соединениях и 100k запросов:
- **Throughput:** ~6000-8000 req/sec
- **Latency (p50):** < 15ms
- **Latency (p99):** < 50ms
- **Success rate:** 100%

Эти показатели подтверждают, что архитектура выдерживает highload с соотношением чтение/запись >> 10:1.

## Технологический стек

- **Go 1.22** — язык разработки
- **NATS** — брокер сообщений
- **Docker** — контейнеризация
- **net/http** — HTTP сервер (stdlib, без фреймворков для минимального overhead)

## Мониторинг

Сервис экспортирует метрики в JSON формате на `/metrics`:
- Количество обработанных событий
- Количество детектированных аномалий
- Счетчики запросов по endpoint'ам
- Время выполнения запросов

Для production можно добавить Prometheus exporter.
